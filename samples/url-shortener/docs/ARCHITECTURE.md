# Architecture — URL Shortener

A single 'Urls' feature on the platform kit. Writes (create link) go through IUrlService → IUrlRepository (EF Core, unique index on Code). The redirect hot path resolves codes through ICacheService (cache-aside, 10 min TTL) and enqueues a ClickEvent on IBackgroundQueue<ClickEvent>, so analytics never add latency; ClickRecorder writes clicks in batches and increments a denormalised ClickCount. Stats are aggregated from click events per link.

## Components
- **Platform kit** (template-locked): database (EF Core, provider-switchable), cache (`ICacheService` + circuit breaker), bounded background queue, rate limiting, request timeouts, health checks, ops stats.
- **Feature code** (`src/App/Features/**`): generated by the orchestrator's agents and validated by its gates.

## Architecture decisions
### ADR-001: 302 instead of 301 redirects
- **Decision:** Return 302 Found for redirects.
- **Rationale:** 301 is cached by browsers, so repeat clicks would never reach the service and analytics would undercount.
- **Alternatives considered:** 301 (cacheable, less load but breaks analytics); 307 (equivalent for GET).

### ADR-002: Random base62 codes instead of a sequential counter
- **Decision:** 7-character codes from a CSPRNG; unique index + up to 5 retries on collision.
- **Rationale:** No coordination between instances (scale-out), codes are not enumerable; 62^7 ≈ 3.5e12 keeps collisions negligible.
- **Alternatives considered:** DB sequence + base62 (needs a single sequence, enumerable); hash of URL (same URL → same code, collision handling still needed).

### ADR-003: Asynchronous, batched click recording
- **Decision:** Redirects enqueue click events; a background worker writes them in batches of up to 200 or every 500 ms.
- **Rationale:** Keeps the hot path to a cache lookup; one transaction per batch instead of one per click relieves the single SQLite writer.
- **Alternatives considered:** Synchronous insert per redirect (simple, but couples redirect latency to DB writes); external broker (durable, needed on Kubernetes, overkill locally).

### ADR-004: Denormalised click counter
- **Decision:** Maintain ShortUrl.ClickCount alongside raw click events.
- **Rationale:** Total clicks are read often; avoids COUNT(*) over a growing table.
- **Alternatives considered:** Always aggregate from events (simpler, slower as data grows).

## Risks
- Clicks in the in-process queue are lost if the process crashes before a flush (accepted locally; use a durable broker on Kubernetes).
- Per-instance memory cache can serve a deleted/changed link until TTL expiry when several instances run (no delete/edit in this version; Redis removes the issue).
- Anonymous creation can be abused for spam/phishing links; mitigated only by rate limiting in this version.

## Assumptions
- Read:write ratio 100:1 (typical for read-heavy services).
- Data retention 90 days.
- Peak traffic = 10× the daily average.

## Strategies for this profile
- Stateless API instances behind the YARP gateway (scripts/run-cluster.ps1) to demonstrate scale-out on one host.
- Cache-aside on the read path (ICacheService) — redirects rarely touch SQLite.
- Analytics written off the request path in batches (bounded queue with load shedding).
- SQLite WAL: many concurrent readers, one writer — the write path is the ceiling.
- Rate limiting per client and request timeouts protect the single host.

## Change log — v2: Optional link expiration

Add an optional ExpiresAt to ShortUrl. Create computes ExpiresAt = now + expiresInMinutes using TimeProvider. The redirect path caches a CachedLink (target + expiry) and evaluates expiry on every request, returning 410 Gone for expired links without recording a click. Metadata and create responses expose expiresAt. No new endpoints.

### ADR-005: 410 Gone for expired links (v2)
- **Decision:** Return 410 with problem details instead of 404.
- **Rationale:** Tells clients the link existed but is permanently unavailable; distinguishes expiry from typos.
- **Alternatives considered:** 404 (hides existence); redirect to an 'expired' page (needs UI, out of scope).

### ADR-006: Relative expiry input, absolute storage (v2)
- **Decision:** Accept expiresInMinutes, store absolute ExpiresAt (UTC).
- **Rationale:** Avoids client clock skew and time-zone mistakes; absolute storage makes the check a simple comparison.
- **Alternatives considered:** Accept absolute expiresAt from clients.

### ADR-007: Check expiry on every request (v2)
- **Decision:** Cache the expiry with the target and compare on each redirect; keep cache TTL unchanged.
- **Rationale:** A cache entry can never serve an expired link, and no DB round-trip is added on cache hits.
- **Alternatives considered:** Shorten cache TTL to the remaining lifetime (more DB load, still racy across instances).

### ADR-008: Keep expired rows (v2)
- **Decision:** Expired links are not deleted.
- **Rationale:** Statistics stay queryable; purge policy can be added later with the retention setting.
- **Alternatives considered:** Delete on expiry (loses analytics).

### Risks introduced
- Production databases need an EF Core migration adding the nullable expires_at column (development SQLite is recreated).
- With a shared Redis cache, entries written by the previous version have a different shape; bump the cache key prefix when deploying.
